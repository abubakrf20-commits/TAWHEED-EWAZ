# به‌روزرسانی برنامه (app/update.json)

این مانیفست در کاتالوگ محتوای GitHub (`TAWHEED-EWAZ/app/update.json`) قرار می‌گیرد
و برنامه هنگام باز کردن صفحهٔ «درباره توحید» آن را بررسی می‌کند.

## نسخه‌بندی شمارندهٔ منجمد (تصمیم ۲۰۲۶-۱۰-۱۷)

اندروید فقط یک APK را رد می‌کند که **versionCode آن کوچک‌تر** باشد؛ یک کدِ *مساوی*
یا بزرگ‌تر روی نسخهٔ قبلی جایگزین می‌شود. از این خاصیت استفاده می‌شود تا کاربر
هیچ‌وقت مجبور به حذف نسخهٔ قدیمی نشود:

| کانال | versionCode | توضیح |
|---|---|---|
| **همهٔ کانال‌ها** | یک عددِ **منجمد** در `android/app/build.gradle.kts` (`FROZEN_VERSION_CODE`) | در طول توسعه ثابت می‌ماند؛ فقط ۱ تا ۱۰ واحد، **فقط پیش از نشر** بالا می‌رود. |
| **split های ABI** | همان عدد + ۱۰۰۰ / + ۲۰۰۰ | فقط برای بیلدهای تفکیکیِ توسعه؛ APK یونیورسال همان عددِ پایه را دارد. |

`pubspec.yaml` (`version: X.Y.Z+CODE`) و `--build-number` دیگر در versionCode نقشی
ندارند (فقط `versionName` = `X.Y.Z` از pubspec خوانده می‌شود).

چرا عدد منجمد؟ عددِ فعلی (`2000012020`) باید بالای *هر کدی* باشد که ممکن است روی
گوشی‌ها دیده شود — نسخهٔ منتشرشدهٔ ۱.۷.۱ کد `2000010013` و بیلد مستقیمِ ۱.۷.۰ کد
`2000004000` داشته‌اند و بیلدهای خارج از repo قدیمی‌تر هم ۶۰۰۹/۸۰۱۰ نصب کرده‌اند.
عدد بزرگ برای کاربر نامرئی است. یک شرط دیگر: **امضای بیلد باید همیشه یکسان بماند**
(همان `android/app/release-key.jks`). اپدیتِ درجا فقط با امضای یکسان پذیرفته
می‌شود؛ دیتای مصحف و بقیهٔ دانلودها در اپدیت حفظ می‌ماند و فقط با uninstall پاک
می‌شود — پس **هرگز کلید امضای release را عوض نکنید**.

چون در بیلدِ منجمد کد در طول توسعه ثابت است، مقایسهٔ «جدید بودن» با یک شمارندهٔ
جداگانه انجام می‌شود — اما در عمل هر دو یکی‌اند: **`revision` = همان عددِ منجمد**.

- هنگام بیلدِ مستقیم: `--dart-define=APP_REVISION=<n>` (ساختِ خودکار با
  `tools/prepare_update.ps1` این را از `FROZEN_VERSION_CODE` پر می‌کند).
- در این فایل: فیلد `revision` و `versionCode` هر دو همان عددِ منجمد.
- برنامه وقتی `revision` را بزرگ‌تر از نسخهٔ نصب‌شده دید، بروزرسانی را نشان می‌دهد.

> مقدار `versionCode` مانیفست برای اپ‌های قدیمی که `revision` نمی‌فهمند نیز
> پشتیبانی می‌شود؛ آن‌ها با `versionCode` مقایسه می‌کنند (در این مانیفست همان عددِ
> منجمد است، پس ماشهٔ بروزرسانی را می‌زنند و همان APK درجا نصب می‌شود).

## وقتی نسخهٔ جدید منتشر شد

1. **عدد منجمد را ۱ تا ۱۰ واحد بالا ببرید** — `FROZEN_VERSION_CODE` در
   `android/app/build.gradle.kts` (و انتظارِ متناظر در
   `test/android/version_code_scheme_test.dart`). این همان bump نشر است؛ در طول
   توسعه **هیچ** bumpی لازم نیست.
2. **بیلد مستقیم** (کد از گریدل می‌آید؛ **universal** بسازید، نه split):
   ```
   flutter build apk --release --dart-define=APP_REVISION=<FROZEN_VERSION_CODE>
   ```
   خروجی: `build\app\outputs\flutter-apk\app-release.apk` (universal با هردو ABI).
   یا ساده‌تر: `.\tools\prepare_update.ps1 -Repo <path>` که بیلد + مانیفست را با هم
   انجام می‌دهد.
3. برای انتشار در **گوگل‌پلی** همان عددِ منجمد در AAB می‌نشیند؛ گارد
   `python tools/check_release_version.py` را پیش از بیلد اجرا کنید.
4. `versionName` = x.y.z؛ `revision` و `versionCode` = همان `FROZEN_VERSION_CODE`.
5. `notes` = فهرست تغییرات (متن ساده).
6. `apkUrl` = لینک مستقیم همان APK (پس از آپلود به `TAWHEED-EWAZ/releases/…`).
7. `playUrl` = لینک گوگل‌پلی (پیش‌فرض همین است).

برنامه فقط وقتی بروزرسانی نشان می‌دهد که `revision` از نسخهٔ نصب‌شده بزرگ‌تر باشد؛
برای بیلدهای مستقیم `apkUrl` و برای بیلدهای play، `playUrl` را باز می‌کند.
