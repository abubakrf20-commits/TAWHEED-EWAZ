# تاریخچهٔ نسخه‌بندی و ریشهٔ دوگانگی versionCode

## مشکل: چرا گوشی 4007 داشت ولی پروژه 2008؟

در ۱۹ آگوست ۲۰۲۶، نصب `app-release.apk` روی گوشی با خطای زیر شکست خورد:

```
INSTALL_FAILED_VERSION_DOWNGRADE: Downgrade detected:
Update version code 2008 is older than current 4007
```

اندروید این خطا را به‌صورت «بستهٔ نامعتبر / الحزمة تبدو غیر صالحه» به کاربر
نشان می‌دهد، بنابراین علت واقعی (downgrade) پنهان می‌ماند.

### دو جریان موازی نسخه‌بندی

| سری | نمونه‌ها | منشأ |
|---|---|---|
| **۲۰۰۰** | 2003 → 2006 → 2007 → 2008 | شاخهٔ release در git (build.gradle.kts) |
| **۴۰۰۰** | 2005، 4007 (و دیگران) | بیلدهای خارج از repo (OpenCode/نصب‌های دستی) |

جزئیات:

- `31cd653` (۱.۳.۲+۱): `versionCode` از `pubspec.yaml` خوانده می‌شد
  (`flutter.versionCode`).
- `42abe9b` (۱.۵.۰): hardcode شد به `2003` در `android/app/build.gradle.kts`.
- `ced9732` (۱.۵.۱): به `2006` ارتقا یافت «تا release روی بیلد قبلیِ 2005 نصب
  شود» — یعنی **2005 در خارج از repo ساخته و نصب شده بود** و در git نیست.
- `58a7a80` (۱.۵.۲): → `2007`.
- `c473361` (۱.۶.۰): → `2008`.
- `1461e7f` (۱.۶.۱): → `4008` تا روی نسخهٔ نصب‌شدهٔ گوشی (4007) نصب شود.
- `3a26a60`: **یکپارچه‌سازی** — `versionCode`/`versionName` دوباره فقط از
  `pubspec.yaml` خوانده می‌شوند (`flutter.versionCode` / `flutter.versionName`).
  > **منسوخ (۲۰۲۶-۱۰-۱۷):** این روش کنار گذاشته شد؛ از این پس یک عددِ منجمد در
  > `build.gradle.kts` تنها منبع است (بخش «نسخه‌بندی با شمارندهٔ منجمد» پایین‌تر).

`4007` در **هیچ شاخهٔ git وجود ندارد** — از یک بیلد خارج از repo (جریان
OpenCode) آمده که از شماره‌های 4000+ استفاده می‌کرد.

## قوانین از این پس

1. **تنها منبع حقیقت**: یک عددِ **منجمد** به نام `FROZEN_VERSION_CODE` در
   `android/app/build.gradle.kts`. `pubspec.yaml` (`version: X.Y.Z+CODE`) و
   `--build-number` **دیگر** در versionCode نقشی ندارند (فقط `versionName` از
   pubspec خوانده می‌شود). تصمیم ۲۰۲۶-۱۰-۱۷.

2. **در طول توسعه هیچ bumpی لازم نیست**: کد ثابت می‌ماند تا همهٔ بیلدهای توسعه درجا
   روی هم نصب شوند و کاربر مجبور به حذف نشود. فقط **پیش از نشر** عدد را ۱ تا ۱۰
   واحد بالا ببرید (و انتظارِ متناظر در
   `test/android/version_code_scheme_test.dart`).

3. **قبل از بیلد، گارد را اجرا کنید**:

   ```bash
   python tools/check_release_version.py
   ```

   اگر گوشی متصل باشد، کد نصب‌شده را با adb می‌خواند و با عددِ منجمد مقایسه
   می‌کند؛ کدهای split روی همان خط (`عدد + 1000/2000`) را می‌پذیرد. در صورت ریسک
   downgrade هشدار می‌دهد (`--fail` برای خروج با خطا، `--fix` برای بالا بردنِ
   یک‌واحدیِ عددِ منجمد).

4. هر بار که عددِ منجمد بالا رفت، این سند و `content/app/update.json` را هم به‌روز
   کنید.

## نسخه‌بندی با شمارندهٔ منجمد (تصمیم ۲۰۲۶-۱۰-۱۷)

اندروید APK را فقط وقتی رد می‌کند که `versionCode` آن **کوچک‌تر** از نصب‌شده باشد؛
کدِ مساوی یا بزرگ‌تر درجا جایگزین می‌شود. پس:

- **همهٔ کانال‌ها (مستقیم / خودمیزبان و پلی):** یک `versionCode` **منجمد** که فقط
  پیش از هر نشر ۱ تا ۱۰ واحد بالا می‌رود. در طول توسعه ثابت است، پس هر بیلد درجا روی
  قبلی می‌نشیند و **هیچ کاربری هرگز مجبور به حذف نسخه نمی‌شود**. جدید بودن را همان
  عددِ منجمد (فیلد `revision` در `update.json` و `--dart-define=APP_REVISION`) تعیین
  می‌کند.
- **split های ABI** فقط برای بیلدهای تفکیکیِ توسعه‌اند و کدشان `عددِ منجمد + 1000`
  (armeabi-v7a) یا `+ 2000` (arm64-v8a) است؛ APK یونیورسال همان عددِ پایه را دارد و
  همین منتشر می‌شود.

چرا عددِ بزرگ (و نه مثلاً ۴۰۰۹)؟ عددِ منجمد باید بالایِ *هر کدی* باشد که می‌تواند
روی گوشی‌ها بنشیند — نسخهٔ منتشرشدهٔ ۱.۷.۱ کد `2000010013`، بیلد مستقیمِ ۱.۷.۰ کد
`2000004000`، و بیلدهای خارج از repo قدیمی‌تر ۶۰۰۹/۸۰۱۰ نصب کرده‌اند؛ اگر عددِ
منجمد کوچک‌تر از هر یک از آن‌ها باشد، بیلد بعدی دوباره downgrade می‌شود. عدد بزرگ
برای کاربر نامرئی است.

نحوهٔ ساخت بیلد (کد از گریدل می‌آید؛ **universal** نه split):
```
flutter build apk --release --dart-define=APP_REVISION=<FROZEN_VERSION_CODE>
```
یا ساده‌تر `.\tools\prepare_update.ps1 -Repo <path>` که بیلد + مانیفست را با هم
انجام می‌دهد.

نکتهٔ مهم: **هرگز کلید امضای release را عوض نکنید.** اپدیتِ درجا فقط با امضای
یکسان پذیرفته می‌شود و دیتا (مصحف و دانلودها) فقط با uninstall پاک می‌شود.

## نسخهٔ فعلی پروژه

- `android/app/build.gradle.kts`: `FROZEN_VERSION_CODE = 2_000_012_020` — منجمد تا
  پیش از نشر بعدی.
- `pubspec.yaml`: `1.8.0+10015` — عددِ `+code` دیگر در versionCode نقشی ندارد؛ فقط
  `versionName` = `1.8.0` از آن خوانده می‌شود. پیش از بیلد پلی هر زمان لازم شد،
  می‌تواند دست‌نخورده بماند.
- مانیفست `content/app/update.json`: `revision`/`versionCode` = همان عددِ منجمد.
- **نشر بعدی**: عددِ منجمد را ۱ تا ۱۰ واحد بالا ببرید (و همان را در
  `update.json` بگذارید)؛ گارد `python tools/check_release_version.py` مطمئن
  می‌شود از هر کدِ نصب‌شده بالاتر است.
